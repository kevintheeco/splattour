# 360 영상 한 번 촬영 → 두 실험 조건 (pano360)

연구 규칙(RESEARCH_DIRECTION.md 4·6번, TERMS.md 마지막 줄): 360° 시점 탐색과 3DGS 자유시점 탐색은 **같은 촬영본**에서 나와야 한다.
`pipeline/splattour/pano360.py` 하나가 360 원본 영상에서 둘을 함께 만든다.

| 조건 | 무엇을 만드나 | 어디서 나오나 |
|---|---|---|
| 3DGS 자유시점 탐색 | `scenes/<name>/` (tour.json, scene.spz, 휴대폰용 scene.mobile.spz) | 영상에서 고른 파노라마 → 한 점을 공유하는 12개 일반 사진(rig) → rig SfM → gsplat |
| 360° 시점 탐색 | `nav.json` + `pano/pNN.jpg` (원본 해상도 등장방형, 발밑 흐림) | **같은 SfM 모델**에 등록된 파노라마 중 약 1.2 m마다 한 장, 방이 바뀌는 곳마다 한 장 |

지점 위치·방향은 3DGS와 같은 좌표(뷰어 세계 좌표: y 위, 바닥 y=0, 미터, tour.json의 splatTransform)라서
평면도, 탐색 범위(capture_path.py), 과업(tasks.json)을 두 조건이 그대로 공유한다.

## 1. 16:30에 할 일 (순서대로)

1. **파일 확인 (1분)**: 받은 폴더에 대고
   ```
   cd pipeline
   .venv\Scripts\python -m splattour.pano360 probe "<받은 폴더>"
   ```
   아래 표를 채운다(출력의 `files[]`, `clips`).
2. **작게 한 번 돌려 보기 (5~10분, 노트북, 돈 안 듦; 8K HEVC는 디코딩이 느림, 급하면 `--seconds 40`)**:
   ```
   .venv\Scripts\python -m splattour.pano360 dry-run "<받은 폴더>" --name wolhajeong360
   ```
   20장, 앞 90초만. `data/pano360/wolhajeong360-dry/` 에 파노라마(equirect/), 잘라 낸 사진(views/), SfM(sfm/), 360 지점(nav/)이 생긴다.
   확인: `sfm.registered_panos` 가 20장 중 대부분인지, `views/pano_camera0/*.jpg` 가 똑바로 서 있는지, `nav/pano/*.jpg` 발밑에 사람이 안 보이는지.
3. **본 처리 (클라우드, 한 줄)**. 먼저 비용만 보기:
   ```
   .venv\Scripts\python -m splattour.pano360 cloud "<받은 폴더>" --name wolhajeong360 --dry-run-cloud
   ```
   괜찮으면 `--dry-run-cloud` 를 빼고 실행. 원본을 R2에 올린 뒤 GPU 서버 하나가 나머지를 다 하고 스스로 꺼진다.
   사이트로 올렸다면("원본만 보관", inbox/<id>/files/*) 노트북을 거치지 않는다:
   ```
   .venv\Scripts\python -m splattour.pano360 cloud --from-inbox <id> --name wolhajeong360
   ```
4. 진행 보기 `... pano360 status --name wolhajeong360`, 끝나면 받기 `... pano360 fetch --name wolhajeong360`
   (360 지점을 앱에 바로 넣으려면 `--apply-space wolhajeong`, 기존 nav.json은 nav.before-pano360.json 으로 남는다. 웹 배포는 따로.)
5. 방 이름: 영상 구간(초)별 방 이름을 `labels.json` 으로 주고 `nav` 단계만 다시 돈다(몇 초):
   ```json
   {"default": "앞마당", "segments": [{"clip": 0, "from": 0, "to": 35.5, "room": "대문"}, {"clip": 0, "from": 35.5, "to": 80, "room": "진입로"}]}
   ```
   클라우드 결과(받아 온 것)에는 `relabel` 을 쓴다(몇 초, 지점 위치·사진은 그대로, 각 지점의 영상 시각으로 방을 정함):
   `... pano360 relabel --name wolhajeong360 --labels labels.json [--apply-space wolhajeong]`
   방 이름을 서버 실행 전에 알면 `cloud ... --labels labels.json` 으로 같이 보내면 방이 바뀌는 곳마다 지점이 하나씩 더 생긴다(권장).

## 2. 받은 파일에서 확인할 것 (probe가 대부분 알려 줌)

| 항목 | 왜 | probe 출력 |
|---|---|---|
| 카메라 기종 | 렌즈 화각(v360 이음 `--fov`), 해상도 | `make`/`model`(Insta360은 비어 있을 수 있음, 파일명 `VID_..._00_...insv`) |
| 형식 | 이어 붙인 등장방형(2:1) / 안 이은 양쪽 어안 | `layout`: `equirect`, `dual-fisheye`, `dual-stream-fisheye`(X3·X4 .insv 한 파일 두 스트림), `insv-lens-00`(ONE X/X2: _00_ 앞, _10_ 뒤 두 파일) |
| 해상도·fps | 5.7K(5760×2880)면 잘라 낸 사진 1834×1284, 8K면 2446×1712 | `width`, `height`, `fps` |
| 길이 | 비용·프레임 수 | `duration` |
| 자이로 | Insta360 Studio가 수평·흔들림을 잡는 데 씀. 우리 v360 이음은 못 씀 | `gyro_or_meta_streams` |
| 몇 대·어떻게 | 아래 3장 | `clips.case`: `single` / `rig` / `passes` / `mixed` |
| 어느 클립이 어느 방 | 방 이름(labels.json) | 연구자에게 직접 물어서 표로 |
| 카메라 높이 | 미터 단위 크기를 정함(`--camera-height`, 기본 1.6 m) | 연구자에게: 셀카봉/삼각대 높이 |

**.insv(안 이은 원본)면**: 가장 좋은 것은 연구자가 Insta360 Studio에서 "360 영상, 등장방형, 원본 해상도, FlowState 켬, 수평 고정"으로 MP4를 내보내 주는 것(렌즈 보정·이음새 섞기가 정확). 그게 안 되면 우리 v360 이음을 쓴다(`--fov` 로 조정, 기본 200°). 이음새가 조금 어긋나도 SfM은 rig 검증이 걸러 주지만, 360 조건의 파노라마에는 이음선이 보일 수 있다.

## 3. 360 카메라 3대 ("360 3대를 이어 붙여서 찍은 것")

probe가 클립 쌍마다 **녹화 시각이 겹치는지**(creation_time + 길이)와 **소리가 같은지**(오디오 포락선 교차상관, `peak_ratio` ≥ 4면 같은 소리, `b_sound_later_by_s` = 같은 소리가 두 번째 클립에서 몇 초 늦게 들리나(= 그만큼 먼저 녹화 시작). rig이면 이 값으로 시각을 맞춰 파일 이름을 공통 시계 순서(`t<밀리초>_c<클립>.jpg`)로 붙여, 같은 순간의 다른 카메라끼리도 매칭되게 한다)를 본다.

- **(a) 3대를 한 막대에 묶어 동시에 촬영 (`case: rig`)**: 세 클립의 모든 파노라마가 한 SfM 모델에 들어간다(각 파노라마 = 12장짜리 rig 한 프레임, 카메라끼리는 특징점 매칭으로 묶임). 높이가 다른 카메라가 시차를 더해 3DGS에 좋다. 서로 몸체가 보이는 부분은 가운데(수평~위) 사진에서는 보통 작다. 360 조건은 **눈높이(1.55 m)에 가장 가까운 카메라 하나**만 쓴다(자동, 또는 `--pano-clip N`).
- **(b) 세 번 따로 걸음 (`case: passes`)**: 역시 한 모델로 합친다. 클립 사이 연결은 어휘 트리 루프 검출(서버에 있음)이 찾는다. 360 조건은 기본으로 눈높이에 가까운 한 클립, 여러 클립 지점을 다 쓰려면 코드의 `pano_clip`을 None으로(모든 클립) 두는 선택지를 연구자와 정한다.
- 시험(합성 2클립, 1.5초 어긋난 같은 소리): `case: rig`, `b_sound_later_by_s: 1.5`, `peak_ratio: 15` 로 맞게 판정. 2클립 20장 → 20/20 파노라마(240/240장)가 한 모델(재투영 0.65 px, 노트북 CPU 4.5분), 360 지점은 한 카메라(clip 1)만.

## 4. 처리 과정 (자세히)

1. **프레임 고르기** (`score_clip`, `select_frames`): 초당 3장 후보를 768×384 흑백으로 디코딩해 (i) 흐림(밝기 정규화 라플라시안, 수평 띠) (ii) 움직임(직전 후보와의 광류 중앙값)을 잰다. 앞뒤 1초, 멈춰 있는 구간(광류 < 0.6 px), 주변보다 많이 흐린 후보를 버리고, **걸은 거리(누적 광류)로 같은 간격**의 칸마다 가장 선명한 후보를 고른다. 기본 300장(클립들에 움직인 양 비율로 나눔). 고른 것만 원본 해상도 JPEG로 뽑는다(`c<클립>_<후보번호>.jpg`).
2. **잘라 내기** (`render_views`): 파노라마 한 장 → 핀홀 12장, 화각 90°×70°: 수평 8장(45° 간격, 서로 45° 겹침) + 위쪽 4장(+50°). **아래를 보는 사진은 없다**(발밑 35° 아래 = 촬영자·셀카봉·삼각대는 학습 사진에 아예 없음). 픽셀 크기는 원본의 각해상도 그대로(8K → 2446×1712). SfM용 마스크: 파노라마의 각 점은 가장 가까운 사진 하나에서만 특징점을 뽑는다.
3. **rig SfM** (`rig_sfm`, pycolmap 4.2): 한 파노라마의 12장은 중심을 공유하는 rig 한 프레임(서로의 회전은 정확히 앎, 고정). rig 기하 검증 매칭(sequential, 앞뒤 10프레임 + 서버에서는 어휘 트리 루프), GLOMAP(global) 매핑, 초점거리·rig 고정. 결과를 PINHOLE 데이터셋으로(`sfm/dense`), 동떨어진 카메라 제거(sfm.clean_model), 파노라마별 위치·방향(`sfm/pano_poses.json`).
4. **학습** (서버): 기존 `cloud.train_gsplat_local`(gsplat MCMC, 원본 해상도) 기본 300만 점·60k 단계(스케줄 2배), 8장마다 1장 시험용(점수) → `build_tour`(바닥·크기·방향 맞춤, 기존과 같음) → `export_web`(spz + 휴대폰용).
5. **360 지점** (`build_nav`): 같은 모델의 파노라마 위치를 tour.json의 splatTransform으로 옮겨, 경로를 따라 `--spacing`(1.2 m)마다 + 방이 바뀔 때마다 한 장. 이웃 = 경로상 앞뒤 + 0.9 m 안의 다른 지점(교차점). `imageYawDeg` = 파노라마 가운데 열이 보는 방향(0 = -Z, 왼쪽으로 돌면 +, capture_path.py와 같은 식). 발밑 62° 아래는 흐리게 덮음(`nadir_patch`). nav.json 형식은 import-360.mjs가 만드는 것과 같다(+ `source`: 어느 영상 몇 초).

## 5. 비용·시간 (L40S급 $0.86/h 기준, 실측 기반 추정)

| 입력 | 사진 수 | 예상 |
|---|---|---|
| 5.7K 영상 5~10분, 파노라마 300장 | 3,600장(1834×1284) | 약 3~4시간 · **$2.5~3.5** (학습 60k 약 1.5~2시간, SfM 약 1시간, 다운로드·디코딩 20분) |
| 8K 영상, 300장 | 3,600장(2446×1712) | 약 4~5시간 · **$3.5~4.5** |
| 빠른 확인 `--steps 30000 --frames 200` | 2,400장 | 약 2시간 · **$1.5~2** |

`cloud --dry-run-cloud` 가 파일 크기·해상도로 다시 계산해 보여 준다. 서버는 `--hours`(기본 6) 뒤 무슨 일이 있어도 스스로 지워진다 → 최악 $5.2.
**잔액 확인**: `pano360 balance` (RunPod 잔액·돌고 있는 서버). 2026-09-25 15:50 기준 잔액 $27.67, 마당 학습 서버(bench-main)가 $1.09/h로 돌고 있음 → 잔액이 이번 작업 최악치보다 적으면 `cloud`가 스스로 멈춘다.

클라우드 실제 실행은 하지 않았다(잔액 공유: 15:55 기준 다른 학습 서버 3대가 합계 $8.2/h로 돌고 있었음). 서버에서만 도는 부분(GPU SIFT, gsplat, 결과 올리기)은 기존에 검증된 코드(cloudjob·maxq가 쓰는 train_gsplat_local, build_tour, export_web, boot.sh 설치 과정)를 그대로 부른다.
처음 실행이 불안하면 작게 먼저: `cloud ... --frames 40 --steps 3000 --hours 1` (약 30~40분, $0.5 안팎).

알게 된 것: 야외(구름·먼 바다)에서는 바닥을 못 찾아 크기 맞춤(align)이 실패했다(경고를 띄움). 한옥처럼 바닥이 보이는 실내·마당에서는 기존 장면들처럼 바닥 RANSAC이 잡는다. 20장/120초는 파노라마 간격이 넓어 두 덩어리로 갈렸다 → 본 처리는 300장(보통 0.3~0.5 m 간격).
